```
├── fuzz/                      Phase 16
├── docs/
│   ├── design/                phase documents (this file, requirements, review)
│   └── adr/                   architecture decision records
├── README.md  ARCHITECTURE.md  DEPENDENCIES.md  CHANGELOG.md
└── BUILD.md  DEVELOPMENT.md  MODEL.md  TRAINING.md  BENCHMARKS.md  SECURITY.md  CONTRIBUTING.md

```

The layout follows from the crate responsibilities in ARCHITECTURE.md §3. It
is not modelled on any other project. Test fixtures are either generated by
committed scripts (procedural patterns, gradients, noise fields) or created by
the project. No third-party test images are committed.

## 2. Interface catalogue

The signatures are indicative. They will be refined as code is written, and
every change will be recorded in the relevant phase commit.

### sf-core
- `Error` / `ErrorKind` (taxonomy in ARCHITECTURE §18), `Result<T>`
- `Limits` — all parser and allocation limits, one struct, validated
- `Size`, `Rect` (checked arithmetic, no silent overflow), `Scale(u8 ∈ {2,4,8})`
- `DType { U8, U16, F16, F32 }`
- `CancelToken` (cloneable, `is_cancelled`, `check() -> Result<()>`)
- `ProgressSink` trait + `ProgressEvent`
- Minimal logging facade (a trait with a default stderr implementation; no
  logging-framework dependency)

### sf-image
- `PixelBuffer`, `PixelLayout { channels, dtype, alpha: None|Straight|Premultiplied }`
- `ImageInfo { size, layout, color: ColorInfo, orientation, format }`
- `RegionSource`, `RegionSink`, `AccessPattern`
- `Codec` trait + `CodecRegistry`; `FormatLimits`
- `color::{IccSummary, TransferClass, WorkingEncoding, encode_to_working, decode_from_working}`
- `resample::{Kernel, resample_separable, area_downsample}`
- `summary::{AnalysisSummary, build_summary(source, spec)}` (patch mosaic + thumbnail)

### sf-model
- `OpSetVersion`, `Op` (enum over the v1 operator set), `OpAttrs`
- `Graph { inputs, outputs, nodes, tensors }`, `NodeId`, `TensorRef`
- `infer_shapes(&Graph, InputShapes) -> Shapes`
- `locality(&Graph) -> Locality { radius, alignment, scale }`
- `required_regions(&Graph, output_region) -> Regions` + crop insertion
- `select_subgraph(&Graph, Variant) -> Graph`
- `plan_memory(&Graph, &Shapes, Precision) -> MemoryPlan`
- `SfmFile::read(bytes/path, &Limits) -> ValidatedModel`, `SfmWriter`

### sf-compute
- `Backend`, `Device`, `Buffer`, `MemoryKind`, `Queue`, `Event`,
  `Executable`, `Bindings`, `DeviceInfo`, `MemoryStatus`, `MemoryRequirement`,
  `Precision`
- `cpu::CpuBackend` with `StrictMode`

### scaleforge (engine and public API)
- `Engine`, `EngineConfig`, `ModelHandle`, `PreparedModel`
- `JobRequest`, `JobPlan`, `JobReport`, `Mode`, `Overrides`, `TilingPolicy`
- Internal modules: `runtime`, `vram`, `hostmem`, `tiling`, `scheduler`,
  `autotune`, `pipeline`, `instrument`, `batch`

### sf-quality
- `psnr`, `psnr_y`, `ssim`, `ms_ssim`, `gradient_fidelity`
- `RegressionRecord`, `compare(prev, next, tolerances) -> Verdict`

## 3. Testing strategy (applies in every phase)

| Level | Where | Runs in this environment |
|-------|-------|--------------------------|
| Unit | Each crate's own tests | Yes |
| Property | Tiling plans (coverage, disjoint cores, alignment), `Rect` arithmetic, memory plans (no overlap of live tensors) | Yes |
| Pipeline | Stage-by-stage, using fixtures | Yes |
| Seam (Q-3) | Tiled vs. whole-image output on the CPU backend | Yes |
| Parity (T-7) | PyTorch DSL vs. Rust CPU runtime | Only after PyTorch is approved and installed |
| GPU | Backend vs. CPU reference, memory accounting | **No**. Needs GPU hardware |
| Fuzz | Codecs, ICC, `.sfm` | Yes (needs `cargo-fuzz`, pending approval) |
| Regression | Model metrics vs. stored records | Yes, once a model exists |
| Performance | Benchmark harness, report only (no pass/fail on CPU timing noise) | Yes (CPU) |

Tests are written together with the code in each phase. Phase 16 adds the
cross-cutting work: end-to-end integration, fuzzing, security tests, and
consolidation of the regression suite.

## 4. Implementation plan with exit criteria

Each phase ends with a self-review, recorded in `CHANGELOG.md`. The phase is
complete only when its **exit criteria** are met.

| Phase | Deliverable | Exit criteria |
|-------|-------------|---------------|
| 5 Core foundation | Workspace, `sf-core` | Tests pass; `Rect`/`Size` arithmetic is overflow-checked with property tests; `clippy -D warnings` is clean |
| 6 Image engine | `sf-image`: buffers, sources/sinks, PNG/JPEG/WebP/TIFF codecs, ICC classification, colour working encodings, resampling, analysis summary | Codec round-trips; limit tests with crafted headers; colour round-trip ≤ 1 LSB (C-1); streaming PNG/TIFF sources read bands with bounded memory (measured) |
| 7 GPU abstraction | `sf-compute` traits + CPU backend with strict mode; `sf-model` graph IR and v1 operator set | Every op has a CPU implementation with reference tests; strict mode catches deliberate misuse in tests; CPU execution is deterministic |
| 8 VRAM and memory mgmt | `vram`, `hostmem` modules | Accounting returns to baseline after success and after injected failures; pre-flight `fits` is correct; arena reuse is shown by tests |
| 9 Tiling | Tile planner (exact and bounded), canonical padding, cores/windows, band order | Property tests (coverage, disjointness, alignment, uniform windows); Q-3 on a synthetic local graph |
| 10 Scheduler | Synchronous executor; pipelined executor behind a flag; reorder buffer | Identical output from both executors; ordering test with injected delays; pipelining stays off by default until measured |
| 11 Model runtime | `.sfm` read/write, validation, locality, required regions, subgraph selection, memory planning; `ModelHandle`/`PreparedModel` | Malformed-file test corpus rejected; derived locality matches hand-computed values; memory-plan predictions match the CPU backend's actual allocations exactly |
| 12 SF-Net | Python DSL + architecture definition + exporter; `MODEL.md` | Exported random-weight model loads in Rust; parity ≤ 1e-4 (**needs approved PyTorch**); receptive radius within budget; `s`-independence test for Faithful mode |
| 13 Training system | Manifests, validation, degradation grammar, pairs, losses, loop, checkpoints, tracking, export; `TRAINING.md` | Determinism test (same seed ⇒ same pairs); licence enforcement test; a small end-to-end run on CPU producing an exported `.sfm`, **explicitly labelled pipeline-validation only** |
| 14 Inference system | Full pipeline and public API: analysis pass → tiles → sinks; auto-tuner (analytic + tuning cache); OOM recovery; batch | End-to-end on CPU with the Phase 13 model; seam test on real images; OOM recovery test via an injected allocator failure; large synthetic image under a small host budget (S-3) |
| 14b GPU backends | CUDA and Vulkan backends | Compiles; op parity and memory tests **written**, but marked **unvalidated** until run on hardware |
| 15 CLI | `upscale`, `batch`, `models`, `devices`, `benchmark`, `doctor`, `eval` | CLI tests; no processing logic in the CLI (review check) |
| 16 Testing | Integration, fuzzing, security tests, regression suite; `SECURITY.md` | Fuzz targets run without findings for a documented duration; path traversal tests pass |
| 17 Benchmarking | Harness, JSON reports, calibration; `BENCHMARKS.md` | Reports contain only measured values; unmeasurable fields are `null` |
| 18 Optimisation | Only changes with before/after measurements | Every optimisation commit cites both measurements |
| 19 Documentation | Complete BUILD, DEVELOPMENT, CONTRIBUTING; all docs reconciled with the code | Docs checked against the code |
| 20 Final review | Written engineering review | Findings fixed or listed as open |

### Deviation from the requested phase order (explained)

1. **The graph IR and operator set move forward from Phase 11 to Phase 7.**
   The GPU abstraction's `compile`/`Executable` interface executes graphs, so
   it cannot be defined without them. Phase 11 still owns the file format,
   validation and static analyses.
2. **CUDA and Vulkan backends move from Phase 7 to Phase 14b.** Two reasons:
   (a) the operator set is frozen only in Phase 12, and writing GPU kernels
   before then would mean rewriting them; (b) there is no GPU here to
   validate them, so they should be written against a stable, CPU-validated
   reference. Phase 7 still delivers the complete abstraction. The
   CPU-semantics risk (R-3) is handled by strict mode.
3. **Tests are not deferred to Phase 16.** Every phase ships its own tests.
   Phase 16 is for cross-cutting test work only.
4. **Training needs user approval first.** Phase 12's parity tests and all of
   Phase 13 need PyTorch, which is not installed and will not be installed
   without approval.
